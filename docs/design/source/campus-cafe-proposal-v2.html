Overview

A campus café needs to take customer orders and keep customers informed. This project builds a small order-tracking system on Azure using serverless services. A customer places an order. Café staff move it through four statuses: Accepted → Preparing → Ready for pickup → Collected. The customer receives an email at each of the first three.

What is new in v2

  • Disaster recovery (page 3): data is copied to a second region (Canada East). A stopped copy of the app waits there. If Canada Central goes down, we follow a 4-step runbook. Target: back online within 4 hours.
  • Security (page 4): six layers of protection, from who can sign in to what code can be deployed.
  • Order of work (page 5): every new item is tagged NOW free, NEXT cents, or LATER costs money.

How it works (numbers match the diagram on page 2)

  1. The customer sends an order: POST /api/orders over HTTPS.
  2. SubmitOrder validates and rate-limits it, saves it as Accepted in the Table, and puts a message on Queue notify.
  3. Staff send a status update: PUT /status (function key today, Entra sign-in next).
  4. UpdateOrderStatus allows only the next valid status, saves it, and queues a message (none for Collected).
  5. The queue message triggers SendNotification. A failed message retries, then moves to the poison queue and raises an alert.
  6. SendNotification sends the email through Azure Communication Services and marks that status as notified.
  7. The customer receives the email (three per order).

Architecture at a glance

  • Primary region, Canada Central: resource group rg-campus-cafe with a Flex Consumption Function App (3 functions), one geo-redundant storage account (Table, Queue, Blob) and Azure Communication Services Email.
  • Platform: managed identity, Application Insights, Log Analytics, alerts, budget. New: Key Vault, Defender for Cloud, Azure Policy with delete locks, Azure outage alerts.
  • DR region, Canada East: rg-campus-cafe-dr with a stopped Function App, a DR Key Vault and a backup storage account. Built from the same Bicep code.

Design principles

  • Serverless, event-driven: pay per execution; the queue decouples HTTP from email.
  • Reliable: retries, poison queue, geo-redundant data, a tested failover runbook.
  • Secure by layers: identity, API checks, secrets, network, detection, safe deployments.
  • Observable: Application Insights + Log Analytics; alerts email the team.
  • Cost-aware: free tiers first; anything that costs real money waits for "later".

Disaster recovery strategy

Pattern: backup and restore with a "pilot light" — a cheap, switched-off copy of the app in a second region
RTO ≤ 4 hoursHow fast we are back online after a region outage.
RPO: minutesHow much recent data we could lose. Geo-copy is not instant and has no time guarantee for tables and queues.

Failover runbook (if Canada Central fails)

  1. Detect: outage alert arrives. Check the storage account's Last Sync Time to see how much data might be missing.
  2. Fail over storage: start the storage account failover. It usually takes under an hour.
  3. Start the DR app: switch on the pilot-light Function App (or deploy it with Bicep).
  4. Switch and fix: give clients the DR URL; re-queue any order whose email was not marked as sent.
After recovery: re-enable geo-redundancy (the account becomes locally redundant after failover), then move back.

What can go wrong, and what protects us

ProblemProtection
A request or instance failsAutomatic retries, then poison queue + alert
One datacenter (zone) goes downStorage keeps copies in 3 zones (GZRS)
The whole region goes downGeo-copy in Canada East + pilot-light app + runbook
Someone deletes or breaks dataDelete locks, soft delete, nightly table export
A bad code releaseRedeploy the previous version from GitHub with Bicep
The email service is downMessages wait in the queue and retry later

How we test it

  • Talk through the runbook as a team (tabletop).
  • Deploy the full stack to Canada East from Bicep, smoke-test, then delete it.
  • Practise a planned failover on a test storage account: no data loss, geo-redundancy kept.

Security strategy

Defence in depth: six layers, so one mistake does not expose the whole system

Threats we cover

ThreatExample in our appControl
SpoofingSomeone pretends to be staffEntra sign-in + MFA
TamperingOrder status changed without permissionRBAC, staff-only endpoint, logs
Repudiation"I never changed that order"Signed-in identity in logs
Information disclosureCustomer emails leakTLS, keyless storage, no PII in logs
Denial of serviceFlood of fake ordersThrottling, max 5 instances, $5 budget
Elevation of privilegeApp gets more access than neededLeast-privilege roles, no stored keys

Two things to know

  • Email abuse: customers type their own email address, so an attacker could make the café email strangers. Throttling per IP and per email, plus fixed email templates, stop this.
  • Network rules apply to the whole Function App. We cannot IP-restrict only the staff endpoint without splitting it into its own app, so staff protection comes from sign-in instead.
Free tools first: Entra security defaults (MFA), Defender for Cloud free tier, Azure Policy, GitHub secret scanning.
